# OpenAC system monitoring

The MIT-owned WindowsTelemetry reader is connected to the dashboard and full system-monitoring view through MonitoringModels/Monitoring. The five sensor groups retain the original two-column / three-column arrangement and scroll independently. New readings update existing row controls; unsupported values remain unknown. Product pictures retain their original image canvas and use uniform scaling. Official pixels and private preview configuration are excluded from public source packages.

Windows processor counters supply interval frequency estimates per logical processor, preserving processor group identity. They are not physical-core sensors or direct BCLK measurements. The tooltip identifies Windows estimates. DDR configuration is reported as MT/s, separately from a measured memory clock. The configured-rate cache is bounded to 90 seconds; ordinary samples expire after 15 seconds, including restored preview snapshots.

NVIDIA data uses the installed driver's read-only nvidia-smi interface. Every GPU keeps its own driver identity, graphics/memory clocks, utilization, memory use and temperature. Driver fan readings are percentages, not RPM. CPU/package/board temperatures, BCLK, current voltages and motherboard fan RPM are not supplied by those interfaces. They are not inferred from nominal values, GPU settings or EURUX controller ports.

Windows volume capacity use and physical-disk active time are separate readings. The first uses total/free capacity; the second uses 100 minus sampled idle time. A valid zero remains zero. NVIDIA availability does not establish AMD/Intel telemetry support.

Monitoring never applies settings, installs drivers, runs SMU/MSR commands or invokes vendor initialization/calibration. Construction is data-only; sampling starts only in a loaded live window on a monitoring page. Closing awaits the outstanding read before disposing counters. Native failures clear the current readings; repeated failure history is bounded.

The exact current-board header names shown as unknown are a source-prepared UI mapping for ROG CROSSHAIR X870E EXTREME. They do not establish readable sensors or general compatibility with another motherboard. The separate installed-AIO TelemetryWorker supports only capability/sensor reads. Its actual five sensor records were zero without sufficient units/device identity, so they are not injected into the monitor. The pure FanModeWorker protocol module likewise has no connected Fan Xpert transport.

WindowsTelemetryTests has 71 synthetic checks and MonitoringTests has 59 synthetic conversion/layout checks. A separate private layout audit checked both 1538/1180 widths and six unshown current-source renders with real Windows/NVIDIA samples. In the actual current sample, the reader obtained 32 logical-processor frequency rows, configured DDR rate, one NVIDIA GPU, three volume capacity readings and disk activity. CPU/board temperatures, motherboard RPM and current voltages remained unknown. No hardware setting was written.

Primary API references: [PDH counter sampling](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhcollectquerydata), [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes), [GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex), [SMBIOS 3.8 Type17 configured memory rate](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.8.0.pdf), [NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/index.html). Implementation and tests were written independently; no G-Helper functions or third-party kernel driver were incorporated.
